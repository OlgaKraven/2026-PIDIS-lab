# Методическая карточка · C3-S5-LR02

> Материал преподавателя. Не публиковать как готовый ответ на студенческом стенде и не включать в шаблон отчёта.

## Цель и навык

- Цель: Составить единый реестр требований по документам заказчика.
- Наблюдаемый навык: Выделять функциональные и нефункциональные требования, ограничения и бизнес-правила, назначать им устойчивые идентификаторы и указывать точный источник.
- Связь с лекцией: Источники требований, Классы требований, Допущения и трассируемость.

## Ожидаемый результат

Реестр из 16–20 атомарных записей четырёх классов с уникальными ID, точными источниками и отметками неопределённости.

## Возможное правильное решение

Смешанные предложения разделяются на самостоятельные записи; функция, показатель качества, внешнее ограничение и бизнес-правило получают отдельные ID и источники.

## Допустимые варианты

Допустима иная детализация реестра, если записи атомарны, классы обоснованы, а источники позволяют повторить вывод.

| Доказательство | Заполненный артефакт и ссылка на строку исходных данных. |

## Типичные ошибки

- Классифицировать требование по отдельному слову или додумывать поведение системы по названию поля.
- Подмена исходного факта предположением без маркировки.
- Отсутствие связи между решением и способом проверки.
- Визуальный результат невозможно прочитать без устного объяснения.

## Подсказка для слабых студентов

Сначала выпишите утверждения с цитатами, затем разделите смешанные записи и только после этого назначьте класс и ID.

Дайте студенту начать с одной строки «факт — источник — решение — проверка», затем предложите повторить структуру для остальных записей.

## Вопросы для обсуждения

- Может ли один фрагмент документа быть источником требований разных классов?
- Как изменится решение при смене ограничения индивидуального варианта?
- Как доказать заказчику, что артефакт готов к следующему этапу?
