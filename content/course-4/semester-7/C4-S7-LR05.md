## Цель

Спроектировать контракт API и документацию, достаточные для независимой реализации и проверки.

## Формируемый навык

Определять endpoint, параметры, преобразование данных, ответы, ошибки, тесты и примеры запросов.

## Ситуация заказчика

Мобильному рабочему месту специалиста нужен API для получения заметок по сервисным работам без прямого доступа к базе данных.

## Исходные данные

- Материалы LR01–LR04.
- Сущности WorkNote, User и ServiceRequest.
- Требования к преобразованию полей API.
- Статусы 200/400/500 и контрольные сценарии тестирования.

Полный пакет материалов: [inputs/course-4/field-service-case.md](https://github.com/OlgaKraven/2026-PIDIS-lab/blob/main/inputs/course-4/field-service-case.md). Все числовые данные и названия в нём являются данными учебной задачи.

## Ограничения

- Используйте только данные учебного кейса, результаты предыдущих работ и указанные лекции.
- Не добавляйте числовые пороги, роли и правила, которых нет в исходных данных; неизвестное оформляйте как вопрос или допущение.
- Схему, таблицу или макет вставьте непосредственно в итоговый DOCX.
- ИИ не требуется; при его добровольном использовании заполните настраиваемую декларацию в отчёте.

## Что необходимо создать

**Спецификация API и проектная документация.** Обязательные поля/элементы: Endpoint/метод, Назначение, Входные параметры, Структура ответа, Ошибки/статусы, Пример/тест.

## Логический маршрут

1. Поймите ситуацию: выделите проблему заказчика и роль, для которой создаётся результат.
2. Отметьте исходные факты и их источники; спорные сведения вынесите отдельно.
3. Выполните анализ: заполните поля «Endpoint/метод, Назначение, Входные параметры, Структура ответа».
4. Создайте проектный артефакт: спецификация api и проектная документация.
5. Ответьте: «Какое решение вы приняли и почему?» — применительно к вопросу «Какие элементы публичного контракта нужны разработчику и тестировщику, а какие детали реализации следует скрыть?».
6. Проверьте результат по критерию: По документу другая команда может одинаково реализовать и проверить API без устных уточнений.
7. Перенесите артефакт и доказательства в файл `C4_S7_LR05_Фамилия_Группа.docx`.

## Что нужно помнить

- Факт из документа и проектное решение записываются раздельно.
- Одна строка артефакта должна содержать один проверяемый тезис.
- Если исходных данных недостаточно, фиксируется вопрос или допущение, а не выдуманный факт.
- Ключевой признак качества: По документу другая команда может одинаково реализовать и проверить API без устных уточнений.
- Типичная ошибка: Описывать только успешный ответ или копировать структуру таблиц базы данных в публичный контракт.

## Небольшой пример формата

GET /api/work-notes без найденных данных возвращает статус 200 и пустой массив [].

Пример показывает способ записи, но не является решением текущего кейса.

## Ожидаемый результат

Контракт endpoint, карта «данные → JSON», матрица статусов, примеры запроса/ответа и три тестовых сценария.

## Требования к Word-отчёту

- Титульный лист с курсом, семестром, номером, темой и идентификатором.
- Цель, практический навык и краткий контекст кейса.
- Основной артефакт: Спецификация API и проектная документация.
- Визуальное подтверждение: таблица, схема, матрица или макет с читаемыми подписями.
- Карточка «Факт — решение — обоснование — критерий — доказательство».
- Самопроверка, короткая рефлексия и ссылки на лекцию и материалы.

LMS принимает **один DOCX-файл**: `C4_S7_LR05_Фамилия_Группа.docx`. Дополнительные файлы не требуются; изображения и схемы вставляются в Word.

## Критерии LMS · 6 баллов

- 2,4 балла — основной проектный артефакт полон и соответствует требуемой форме.
- 1,2 балла — анализ корректен, противоречия и неопределённости замечены.
- 1,2 балла — решение явно связано с исходными данными.
- 0,6 балла — указан выполнимый критерий проверки и доказательство.
- 0,6 балла — выполнены самопроверка и содержательная рефлексия.

## Чек-лист самопроверки

- Артефакт заполнен полностью и имеет идентификаторы/подписи.
- Каждый существенный вывод связан с исходным фактом.
- Допущения не выданы за подтверждённые сведения.
- Визуальный результат читаем без устного пояснения.
- Решение, критерий проверки и доказательство согласованы.
- В DOCX нет готовых ответов из чужого проекта и лишней теоретической главы.
